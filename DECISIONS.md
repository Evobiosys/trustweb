### D13 — Relay two-hop consent chain (Task 1, [S5]/I8): 3-party room is minted fresh, Timo's own 2-party room is discarded
Implementing the second_brain relay (Anna relays Ben's REQUEST to Timo, the noted owner) hits a hard TransportAdapter limitation: `createSharedRoom` can only mint a brand-new room for a given peer list — there is no invite-a-peer-into-an-existing-room primitive on either InMemoryTransport (in-tree) or the MatrixTransport interface it's meant to swap with (I5). Once Timo consents, his own `completeConsent` has already opened (and sent CONSENT+INTRO into) a 2-party room with just himself and Anna — that room is functionally correct for a *direct* ask but wrong for the *relay* case, which needs Ben in it too.

Resolution: Anna (the relay hub) discards Timo's 2-party room unused and calls `createSharedRoom([ben, timo, anna])` herself on receipt of Timo's CONSENT, then sends CONSENT+INTRO upstream to Ben and a courtesy INTRO to Timo pointing at the *new* room id. This keeps the protocol frozen at v0.1 (composition of existing REQUEST/STATUS/CONSENT/INTRO, no new envelope type, no `createSharedRoom` signature change) at the cost of one wasted room mint per successful relay. Follow-on gap surfaced by the same limitation and fixed in the same change: INTRO's body is `{room_id}` only, so neither Ben's nor Timo's daemon can learn a third party's peer id from the envelope alone — closed by having Timo's daemon post a real room-chat message (the existing `RoomMessage`/`sendRoomMessage` extension already documented in `in_memory_transport.ts` as the sanctioned gap-fill over the frozen envelope set) on joining, and having `onRoomMessage` register any as-yet-unlisted sender into the local room's peer list. A future task should consider a real "invite" primitive on TransportAdapter (or an explicit peer-list field on INTRO) so this stops needing a courtesy room-chat message to converge.

### D15 — Relay decline is wire-silent upstream, not a forwarded PASS (Task 1 review fix, I3/I8)
Task 1's brief said the relay hub "sends the uniform PASS upstream" once the noted owner's downstream leg resolves to PASS (declined or no match). Review found this violates I3/I8: `PENDING -> PASS` is a wire pattern that occurs *only* on the relay path — a direct decline-after-dispatch is silence after PENDING (`decline()`'s existing behavior) — so an asker who ever sees a second STATUS after PENDING can infer relaying happened, which I8 explicitly forbids ("no hop reveals more than a direct request"). The forwarded PASS was also functionally inert: `askerHandleStatus` early-returns once `internal_state` has left "open", which the earlier PENDING already guarantees.

Supersedes the brief's literal instruction: on downstream PASS, `relayHandleStatus` now resolves the relay link (`state: "failed"`) and the upstream consent card *internally only* — card state goes `inactive` ("could not help"), audit-logged (I6) — and sends nothing further upstream. The asker's own ask degrades to `no_one_this_time` purely via its own TTL, identical in shape to a direct decline-after-PENDING. Verified by rewriting the I3 relay test to compare relay-decline against relay-no-match (not a top-level direct no-match) with topology held constant, asserting full-sequence byte-identical STATUS envelopes at the asker (not just the last one) — see `daemon.test.ts`'s relay `describe` block.
Integrator-approved additive extension of the frozen v0.1 protocol: `TrustEdge.level` (`contact`/`friend`/`close`, default `friend`, I9), `SharePolicyAudienceSchema` gains `close` and `public` (reused as a listing's `tier`), and three new envelope types — LISTING (offer/gathering, `tier`+`steps`+`via`+`state`), LOAN (borrow lifecycle), DM (direct chat) — all sharing the existing `{v, type, request_id, ts, body}` shape; version string stays `"0.1"`. `packages/protocol/src/schemas.test.ts`'s old "`audience: 'public'` throws" assertion was updated to a genuinely bogus value (`carrier_pigeon`) since `public` is now valid — a required, deliberate change, not scope creep.

Interpretation calls made explicit here (brief left them as exact schema shapes + prose behavior, not full state-machine detail):
- **`private` tier = local-only.** A listing published at tier `private` is stored but never sent to any edge — mirrors `evaluatePolicy`'s existing `private` handling for Items, and is the concrete form "Private = invisible" takes for listings (never a locked/teaser state; the peer receives nothing, full stop, because nothing is ever sent).
- **Tier -> level gate:** `close` requires trust level `close` exactly; `trusted` requires `close` OR `friend`; `wot_commons`/`public` reach every non-expired edge regardless of level (`public`'s additional guest/unauthenticated API exposure is Task 5's concern — this layer only guarantees it is at least as open as `wot_commons`).
- **`policy.ts` guard for the new audience values on Items:** adding `close`/`public` to the shared enum would otherwise make an Item audience `close` fall through `evaluatePolicy` into the no-edge-required branch — *more* permissive than `trusted`, an I1 direction. Added a one-line guard: `close` requires a valid edge specifically at level `close`; `public` behaves like `wot_commons` (no edge required). No shipped Item fixture used these values, so no existing test's behavior changed, but leaving the gap unguarded would have been a silent I1 regression the moment any Item adopted the new values.
- **Forwarding / "origin" exclusion:** a receiver forwards a LISTING once per `(listing_id, state)` pair (tracked via a `forwarded` flag on `ReceivedListingRecord`, reset when the incoming `state` differs from what's stored) — this is what re-propagates a withdrawal through the same tree the original publish reached, and what stops a duplicate delivery of the same state from re-forwarding forever in a trust graph with cycles. The brief's "excluding origin + already-via peers" is implemented as `{from, ...via}`, which only excludes the *original owner* through one hop (forwarders append themselves to `via`, never the owner, since a publish starts with `via: []`) — closed origin-safely, under either reading of "origin", by having `receiveListing` ignore any `listing_id` that is already in this persona's own `listings` table (i.e. skip outright if *I* am the owner), regardless of who sent it or what `via` says. Verified with a 3-persona cyclic-trust-graph test (`daemon/listings.test.ts`).
- **`close`-tier listings are never forwarded, full stop** — regardless of remaining `steps` or whether the sender-edge/target-edge levels would otherwise qualify. Inner room stays inner.
- **Borrow is alpha/direct-connection-only.** `requestBorrow` throws if the received listing arrived via a forward (`via.length > 0`) — a forwarded listing's actual owner peer id is never learned by intermediate hops, only their display name. Via-chain borrow is deferred to the existing relay/ask flow (already noted in FUTURE.md's "Second-degree borrow via via-chain" entry, predating this task).
- **Loan completion is per-side, and "owner confirm" is folded into the same check-in call.** The LOAN state enum has no separate "confirmed" state; `checkInLoanCompletion(loanId, "complete"|"not_yet", detail?)` is callable by either the owner or the borrower once the loan is `returned` (or already reads as a completion outcome locally, if the counterparty's own report arrived first and synced the view — both sides still act independently, this just avoids an artificial reordering constraint). `detail` is stored in `LoanRecord.completion_detail` and is **never** placed on the wire for either outcome, not just `not_yet` — an explanatory check-in note is always this persona's own private annotation (mockup RES-5); only the coarse `complete`/`not_yet` marker crosses the wire. Verified by asserting the detail string never appears anywhere in the captured outbound envelope log.
- **DMs are connected-only on both send and receive.** `sendDm` throws if there is no trust edge to the target peer; `receiveDm` silently drops an incoming DM from a peer with no trust edge (defense in depth — a well-behaved sender's own `sendDm` already guards this, but the receiver doesn't trust that).

Store additions (`packages/agent-daemon/src/store/`): `listings`, `received_listings`, `loans`, `dm_messages` tables, following the existing JSON-column/upsert pattern; `trust_edges` gained a `level` column (`NOT NULL DEFAULT 'friend'`). Daemon logic extracted into a new `packages/agent-daemon/src/daemon/listings.ts` module (free functions over a small `ListingsDeps` bag, same composition style as `steward.ts`) rather than growing `daemon.ts` further — `daemon.ts` gained only thin delegating methods plus three new `handleEnvelope` switch cases (LISTING/LOAN/DM). Audit entries for all D14 actions reuse the existing `logOwner` (actor: `"owner"`) audit channel — the frozen `DecisionLogEntrySchema.actor` enum (`"asker"|"owner"`) was left untouched (out of this task's file list) since I2's asker-redaction discipline doesn't apply to this feature's privacy model (filtering happens at send time, not at audit-read time), so reusing `"owner"` for a borrower-side or DM action is a label-of-convenience, not an I2 concern.

### D16 — Relay requires a live trust edge to the noted owner; unreachable owner degrades to no-match (Task 1 review fix, I3/I8, pre-seam for solo-mode)

An architecture-seam review (`docs/research/solo-graph-extension.md` §5, done ahead of solo-mode's own Contact/local-only-peer work) found `ownerHandleRequest` (`daemon.ts`, formerly ~line 355) treats *any* incoming-REQUEST match on a `provenance.kind === "second_brain"` item as relay-eligible with no check that `item.provenance.owner` is a reachable peer — `forwardRelay` then calls `transport.send(notedOwner, ...)` directly. `Provenance.owner` is a bare `PeerId` (`z.string().min(1)`); nothing today stops it from pointing at a non-peer string, and once local-only `Contact`s exist (solo-mode) a noted owner routinely will not be a connected peer at all. Untouched, this either throws mid-flight or misroutes, and breaks the D1.6 promise that the noted owner is pinged for consent before their having a resource is disclosed. `forwardRelay` predates D14 and never got the D14 "connected-only, defense in depth" guard already applied to `sendDm`/`receiveDm`/`receiveLoan` (`listings.ts`).

Fix: before a second_brain match is allowed to become a relay consent card (or auto-forward), `ownerHandleRequest` now requires `store.getTrustEdge(item.provenance.owner)` to exist AND be unexpired, reusing the same expiry predicate `sendAsk`'s fan-out eligibility already uses (`new Date(edge.expires_at).getTime() > now.getTime()`, `daemon.ts:145`). If the check fails, the match is folded back into the *same* `matched === undefined` branch that handles a genuine no-match — not a separate early return — so the resulting PASS is byte-identical on the wire to any other no-match (I3) by construction: same uniform delay, same `statusEnvelope(requestId, ts, "PASS")`, same `"status_pass"` audit entry. No consent card is ever created and the middle hop's human is never pinged. The only difference is a local-only audit entry (I6) logged before the fallthrough — action `relay_skipped_unreachable_owner`, naming both the matched item and the unreachable owner id — never sent on the wire, so it does not leak into the asker's I2-sanitized view.

Scope: this is a defensive guard against a gap that exists today (a hand-edited or malformed `provenance.owner`) and a deliberate pre-seam for solo-mode's `Contact` type, which has no transport-reachable `PeerId` a trust edge could ever be keyed on. It changes zero v0.1 behavior — every shipped second_brain fixture's noted owner already carries a live trust edge (D13's Anna/Ben/Timo scenario) — and needs no protocol/schema change; `PeerIdSchema`'s permissiveness was never the bug, only the missing runtime check was. Verified by two new tests in `daemon.test.ts`'s relay `describe` block: a second_brain item whose noted owner has no trust edge at all, and one whose edge has expired — both assert no consent card, a wire-byte-identical PASS against a genuine-no-match control, and the local audit entry naming the skipped owner. All pre-existing relay tests (happy path, I3 decline/no-match pair, auto_forward) stay green unmodified.

### D18 — Task 4: consent-gated inbound CONNECT (origin-node onboarding). Two new envelope types, dedicated store record, both handshake directions.

Additive to the frozen v0.1 protocol (integrator-approved; version string stays `"0.1"`): two new envelope types, `CONNECT` and `CONNECT_ACK`, both sharing the existing `{v, type, request_id, ts, body}` shape. A brand-new self-sovereign peer (a browser that generated its own DID, holding NO prior trust edge) sends `CONNECT { display, relay?, level? }` to an origin it scanned; the origin OWNER approves a consent card; on approval both sides gain a reciprocal trust edge. `CONNECT_ACK { accepted, display? }` echoes the CONNECT's `request_id` for correlation.

**New types, not reused INTRO/CONSENT:** INTRO/CONSENT are room-oriented (they belong to an already-consented resource request and carry `room_id`/`conditions`). A connect handshake is pre-relationship and forms an edge, not a room — overloading them would have forced a fake `request_id`/room semantics and blurred two distinct lifecycles. A dedicated pair keeps each envelope's meaning singular (the same reasoning D14 used for LISTING/LOAN/DM).

**CONNECT is the ONE inbound envelope accepted from an edge-less peer.** `handleEnvelope` gains `CONNECT`/`CONNECT_ACK` cases; everything else stays effectively connected-only as before. On CONNECT the daemon creates a **pending inbound connect card** (a dedicated `connect_cards` store table + `ConnectRecord`, NOT the `incoming` consent-card table — a connect has no matched item, and `sanitize.ts`'s consent-card view throws on a missing item, and the I3 uniform-delay STATUS machinery does not apply). It NEVER auto-creates an edge (I4 consent-gated). The card surfaces owner-side in `/api/state`'s new `connect_cards[]` with full requester context per I4 (requester DID + display).

**Endpoints:** `POST /api/connect/accept { card_id, level? }` and `POST /api/connect/decline { card_id }` (exact-path — they do NOT collide with Task 8's `POST /api/connect` QR direct-trust-add). Accept forms a `TrustEdge` to the new peer (level = the owner's explicit choice if given, else the clamped requested level; `expires_at` +1y via `daemon.addTrust`, I9) AND sends `CONNECT_ACK{accepted:true, display:<origin display>}` so the new peer can form ITS edge. Decline sends `CONNECT_ACK{accepted:false}` — a gentle, minimal "not accepted" that reveals nothing further (origin-node model: the owner simply decided). This is NOT the I3 resource flow (a connect is not a PASS), so an explicit `accepted:false` is correct, not a leak.

**Level clamp (I9, no auto-escalation):** the CONNECT body's `level` is a wish, never binding. `clampConnectLevel` grants `contact` if requested (a looser level), else caps at `friend` — the daemon can't know the app skin's per-context default (ecstatic `friend`/family `close`/business `contact`), so `friend` is its conservative self-granted cap. An owner passing an explicit `level` to `acceptConnect` is a sovereign I4 override, not auto-escalation.

**Both handshake directions implemented (daemon↔daemon testable without the browser):** `sendConnect` records an OUTBOUND pending `ConnectRecord`; a later `CONNECT_ACK` is actioned only if it matches an outbound record by `request_id` AND its transport-authenticated sender equals that record's target peer — an unsolicited `CONNECT_ACK{accepted:true}` can never conjure an edge. On accept the new peer forms its reciprocal edge (display from the ACK, level at its own conservative default). The connecting DID is always the transport-authenticated `from`, never a body-claimed identity (the envelope has no `from` field; CONNECT's body is `.strict()` so an injected `from` key is rejected).

**Abuse guard:** at most one pending inbound connect card per requester DID — a repeat CONNECT refreshes the existing card (latest `request_id`/display) rather than piling up. Deeper rate limiting (cross-requester flood, outbound-record dedupe, edge-already-exists short-circuit, honouring the `relay` routing hint on a real transport) is noted as known-debt (FUTURE.md), not built for the alpha.

**Auditability (I6):** connect received / accepted / declined / ack-accepted / ack-declined / ack-ignored all log via `logOwner` (actor `"owner"`). Connect is NOT the I2-blind asker flow — the local user legitimately knows the counterparty (they chose it / it scanned them), so naming the peer is correct; `logAsker` would in fact throw on a peer id (`sanitize.ts`). This reuses D14's sanctioned "label-of-convenience" precedent for non-resource-flow owner actions.

**WS surfacing (brief-vs-code note):** the brief asked to mirror the existing consent-card pattern's "WS `consent_card` event". In the actual codebase that event type is declared in `server.ts`'s `WsEvent` union but NEVER broadcast — relay/direct consent cards surface purely via the generic `state_changed` event (`daemon.notifyChange`) + a `/api/state` refetch. Faithfully mirroring the REAL pattern, connect cards surface the same way: `state_changed` + `connect_cards[]` in `/api/state`. Wiring a bespoke typed daemon→server callback just for connect cards would be inconsistent (resource consent cards get none) and would touch the shared onChange contract. Flagged as a minor concern in the task report; not a functional gap.

Tests: `packages/protocol/src/envelope.test.ts` (CONNECT/CONNECT_ACK parse + strict-reject), `packages/agent-daemon/src/daemon/connect.test.ts` (two edge-less daemons via the harness's new `seedEdges:false` option — pending card + no edge; accept → both edges, requested `close` clamped to `friend`; owner explicit `close` override; decline → no edge + `accepted:false` + nothing leaked; duplicate CONNECT → one card; unsolicited CONNECT_ACK → no edge). ### D19 — network-access package: consent-ladder + k-anonymity for "access to my network" (solo mode, 2026-08-08)

New sidecar package `packages/network-access` (no daemon coupling yet): the owner offers introductions from a private contact inventory behind three gates — Gate 0 may-query (`blocked`/`ask_each_time` default per I9/`standing_allow`), Gate 1 run-now with owner model choice (small keeps the machine usable / large), Gate 2 reveal. Pure reducer (`gates.ts`), all I/O effects returned as data; `requesterView()` is the single asker-facing view builder (I2 chokepoint pattern). Matching = injected LLM stage (Ollama chat, strict JSON, `<think>`-tolerant) with keyword fallback — survives with no LLM (matcher-chain philosophy).

**k-anonymity floor (new, k=3 default):** an anonymized aggregate ("4 of 12 match") is released only at ≥k matches. ### D25 — Demo 21: the uniform relay deadline, and why it applies to every ending on A's hop, not only the relay ones (RELAY_DEADLINE_MS, gate.ts)

docs/two-hop-decisions.md §4 found that I3 (indistinguishable no) holds at the wire-byte level even across a relay, but that ELAPSED TIME to any terminal outcome is a hop-count oracle unless closed: a relay structurally cannot resolve inside one hop's own uniform reply window (GATE_BUDGET_MS, 900ms — sized for one human's own machine-time equalisation, not a second hop's full round trip), so a fast answer would mean "never left A" and a slow one "reached, or is travelling toward, hop 2," regardless of what the bytes said. `apps/demo`'s answer model is one synchronous round trip B is watching happen (no representation for "still travelling to hop 2," unlike the daemon's async, hours-long `ttl_ms`), which the same document names as an open architectural fork with exactly two honest resolutions: invent a new "still travelling" state (a new observable needing its own indistinguishability argument from scratch), or hold B's answer to the deadline of the EXISTING single round trip so a one-hop "nothing" takes roughly as long as a two-hop one.

**Chosen: the second option.** `gate.ts`'s new `RELAY_DEADLINE_MS` (30 000 ms — this project's own already-stated I3 default, `CLAUDE.md`: "default 30 s, no jitter," reused rather than invented) is the ONE anchor every ending on A's hop is held to, via `emitAnswer`'s new optional `opts.deadline` override and `main.ts`'s `sendSecondHopFinalAnswer`: a genuine no-match, a declined relay, a declined-to-be-named Jakob, a real Jakob no-match, and a relay that never got an answer in time all fire A's ONE AnswerEnvelope to B at exactly `receivedAt + RELAY_DEADLINE_MS`, content computed at fire time — never earlier, regardless of how quickly the underlying decision resolved. This is deliberately NOT scoped to only the relay-attempted paths: A's own DIRECT match (had A had one) is held to the identical deadline, so "A answered directly" and "A relayed and got nothing" cannot be told apart by the clock either. If Jakob answers after the deadline, D15's own discipline is followed exactly: no second message to B, ever — the late arrival is recorded locally (I6) and dropped.

Byte-level proof: `test/second_hop_gate.test.ts` (pure-function, five nothing-causes at a fixed qid, plus the real `decide()` call `declineRelay` actually makes) and `test/e2e/second_hop.mjs` (live relay, three real device identities, seven legs including two nothing-causes at one pinned qid over the network both times). Timing proof (injected clock, no real 30 s wait): `test/second_hop_timing.test.ts`.

**Two further structural choices, stated briefly:**
- **I8 depth cap ("one hop, not N"):** `QueryEnvelope.relayed?: true` (additive, strict-parsed like `did`/`freeText`) marks a query a hop already forwarded once. A device handling a `relayed: true` query never itself offers to relay it further (`runSecondHopRelayCeremony`'s `note = !q.relayed ? ... : undefined`), regardless of what it privately knows — enforced structurally, not only by there being three devices in this scenario. No field anywhere lets B request a hop count.
- **Deploy:** `scripts/deploy_wot.sh` builds and pushes `/wot/demo21/` unconditionally, like demo1/2/3/6 — unlike demo 20's opt-in gate, demo 21's seed content (a ladder, `data/second_hop.ts`) is generic rather than the owner's real address, so the sensitivity demo 20's gate exists for does not apply here.

### D26 — Demo 21: D25's own deadline mechanism was wrong; fixed by arming the send at receipt, not at decision time

Post-review of D25 found that its implementation did not actually deliver what it claimed. `emitAnswer`'s `opts.deadline` override and `sendSecondHopFinalAnswer` both called `settleAt(receivedAt, RELAY_DEADLINE_MS)` from INSIDE each ending, i.e. AFTER a human (A, or Jakob via A's own bounded wait) had already decided. `settleAt` resolves IMMEDIATELY once its target instant has already passed (its own doc comment says so, and D25's regression pass never exercised this — no test called it with an elapsed t0). Consequence: any ending reached after a human took longer than `RELAY_DEADLINE_MS` to decide fired the moment that human acted, not at the fixed deadline — reopening exactly the hop-count oracle D25 exists to close ("arrived at 30.0s" = automatic nothing; "arrived later" = a human, somewhere, was involved; "arrived even later" = a full Jakob round trip). `secondHopWaitHonesty`'s on-screen claim ("this takes up to 30 seconds either way, regardless of outcome or how far the question travelled") and D25's own text were both false under this bug whenever A (or Jakob) deliberated past the window.

**Fix:** `main.ts`'s new `createRelayDispatch(q, peer, receivedAt)` arms ONE `setTimeout` at `receivedAt + RELAY_DEADLINE_MS`, unconditionally, before any human interaction can happen — the same shape `packages/agent-daemon`'s `scheduleAt`/`dispatchOwnerStatus` already uses (content read at fire time, fire time fixed at receipt). Every ending (direct match yes/no via `decide()`, relay decline via `decide()`, relay accept via `dispatch.resolvePayload()` once Jakob's round trip concludes or times out) only ever calls `dispatch.resolve()`/`resolvePayload()`, which UPDATES what will be sent — it never sends anything itself. A `resolve()` call after the timer already fired is a documented no-op: the "nothing" already went out; the late decision is simply too late, exactly like Jakob answering after the deadline already was. `runSecondHopRelayCeremony`, `renderSecondHopDirectCard`, `renderSecondHopRelayCard`, and `forwardToOwner` were restructured around this dispatch; `emitAnswer`'s now-dead `opts.deadline` override (unused by any caller — demo 21 no longer routes through `emitAnswer` for any second-hop ending) was removed, restoring it to its pre-demo-21 shape.

**UI consequence handled explicitly, not left implicit:** holding the send to a fixed deadline independent of tap time means a card left visible after being tapped would sit there, clickable, for up to the remainder of the window. `renderSecondHopPendingScreen()` (new; i18n `secondHopPending`) replaces the card the instant a decision is recorded, saying only that the decision is noted and will go out on the same schedule as any other answer — never claiming anything about outcome or hop distance.

**Two smaller findings from the same review, both fixed:**
- `secondHopAskHonesty`/`secondHopChainHonesty` on `screenAsk()` were gated on `wotScenario() === 'secondHop'` alone, a build-time flag shared by all three devices in this scenario — rendering a false claim ("your question does not go straight to Jakob") on Jakob's own ask screen, and on A's ask screen when she asks Jakob directly (no relay involved). Gated instead on `isLeafAsker` (`s.me.id !== 'jakob' && !s.secondBrainNote`), true only for B.
- `runSecondHopRelayCeremony`'s owner-peer lookup gained `p.id !== q.from.id`: A must never offer to relay a question back to its own requester (Jakob asking A, matched against A's note about Jakob, would otherwise render a relay offer to forward Jakob's own question back to Jakob) — same sender-exclusion reasoning D14's own relay logic already applies elsewhere in this app.

Byte/timing proof: `test/e2e/second_hop.mjs` leg 8 (new) reproduces the fixed dispatch pattern against the live relay with a short local deadline — 8a proves a resolve reached before the deadline still waits for it (not sent early); 8b proves a resolve arriving after the deadline already fired is a no-op (exactly one envelope reaches B, content "nothing", not the late decision). `test/second_hop_timing.test.ts` (unchanged, fake-timer, isolated `settleAt` proof) and `test/second_hop_gate.test.ts` (unchanged, pure byte-identity proof) still hold — the bug was in the WIRING between the timer and the send, not in either primitive.

### D30 — Demo 21: two independent timing switches, not one — the relayer's own switch, and the interaction it cannot fully close

D28 gave "the person being asked" a single per-person switch, defaulting to fast. The owner's refinement, approved: there are actually TWO roles, held by the SAME device (A) but distinct in what each one exposes, and they get two SEPARATE switches with DIFFERENT defaults:

- **The person ANSWERING** (a real match against her own stuff, or a genuine immediate "nothing" — no note ever in play) controls whether the asker may learn how far the question travelled. Default (D28, unchanged): FAST — the owner's own explicit I9 override, because this person was directly asked and at least gets to decide whether to share at all.
- **The person RELAYING** (an eligible second-brain note is in play at all — whether she goes on to decline it or to forward it) controls whether it may be revealed that she passed the question on. Default: NOT-revealing (uniform, ordinary I9, NOT overridden) — "the relayer never asked to be involved" (owner's own words). Declining is included in this class, not only forwarding: if declining resolved fast while forwarding resolved slow, the TIMING GAP between the two would itself reveal "she had a note to consider" vs not — the exact leak the switch exists to close — so both share the one uniform default together.

**Implementation.** `state.ts` gained TWO fields: `secondHopUniformModeDirect` (governs `kind: 'direct'` endings, default false = fast) and `secondHopRevealRelay` (governs `kind: 'relay'` endings, default false = uniform/non-revealing — note the INVERTED polarity from the direct switch, intentional, each field's own doc comment says so explicitly to avoid the two being confused). `createRelayDispatch`'s `resolve()`/`resolvePayload()` take the `kind` as an explicit argument from each call site (`renderSecondHopDirectCard`, the `!tpl`/nothing-eligible branches → `'direct'`; `declineRelay`, `forwardToOwner`'s final resolution → `'relay'`) and look up the correct field per kind. **The interaction, said rather than papered over (owner's own instruction).** Because the two switches' DEFAULTS point in opposite directions — direct fast, relay uniform/~30s — a relay-eligible ending is, AT DEFAULT SETTINGS ON BOTH SWITCHES, still observably slower than a direct-or-nothing one.
